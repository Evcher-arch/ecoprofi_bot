# Пользовательский API Mini App v1

**Статус:** контракт для реализации, 2026-11-23. Base path `/api/miniapp/v1`. JSON UTF-8, UUID в строковом виде, время UTC ISO 8601. Неизвестные поля тела отклоняются. Тело до 32 KiB; launch_query до 16 KiB UTF-8. Все ответы API имеют `Cache-Control: no-store`.

## Авторизация и ошибки

После входа — `Authorization: Bearer <случайный токен>`. Токен никогда не передаётся в URL, тексте вопроса или идентификаторе диалога. Сервер берёт личность из сессии. Все маршруты с данными защищены общей проверкой допуска, включая опрос статуса. Завершение сессии требует действительный токен, но не подписку.

Ошибка: `{ "error": { "code": "…", "message": "…", "retryable": false }, "operation_id": "…" }`. Нет исходного тела, параметров запуска, traceback, карточек или чужих идентификаторов. Validation handler не возвращает поле `input` с переданным значением. Ссылка на клуб, если нужна, отдельное поле `club_url` с настроенным стабильным HTTPS-адресом.

| HTTP | Коды | Поведение |
| --- | --- | --- |
| 401 | invalid_launch, launch_expired, session_expired, resume_mismatch | Открыть приложение заново из VK; очистить локальную сессию при её недействительности. |
| 403 | not_subscribed | Экран подписки, без истории; исключения проходят общий допуск. |
| 404 | not_found | Нет такого объекта в этой сессии; чужой объект неотличим от отсутствующего. |
| 409 | request_conflict, dialog_busy, dialog_closed, retry_superseded | Не менять первоначальную запись; исправить действие по коду. |
| 413 / 422 | payload_too_large / invalid_input | Не искать и не обращаться к модели; сохранить редактируемый текст на клиенте. |
| 429 | queue_full, session_limit, rate_limited | Retry-After для временного ограничения; при лимите сессии предложить новый вход. |
| 503 | membership_unavailable, service_unavailable | Временная ошибка без материалов, повтор после восстановления. |

Проверка сессии/владения предшествует раскрытию объекта. Допуск проверяется до чтения истории и повторной выдачи; отказ при подготовке результата не позволяет вернуть ранее вычисленные материалы. Нормальный результат опроса может содержать состояние `retryable_failed` с HTTP 200 — запрос к статусу успешен, сама обработка нет.

## POST /session — новый вход

Тело: `{ "launch_query": "vk_app_id=…&vk_user_id=…&vk_ts=…&sign=…" }`. Передаётся исходная query без начального `?`, не URL целиком. Это схематичный пример, не тестовый секрет.

Порядок: строго разобрать percent-encoding/UTF-8; отклонить дубли ключей, отсутствие обязательных `sign`, `vk_app_id`, `vk_user_id`, `vk_ts`; выбрать все `vk_*` (включая неизвестные), сохранить пустые значения, отсортировать ключи, применить urlencode, HMAC-SHA256 и Base64url без padding. Проверить `sign` через constant-time compare, ожидаемый `MINIAPP_APP_ID`, положительный user ID, `now-300 ≤ vk_ts ≤ now+60`. Поля роли/сообщества из запуска не заменяют подписку и не добавляют исключений.

Затем общий допуск. При успехе атомарно создать сессию и первый диалог. `201`: `{ "token": "…", "expires_at": "…", "dialog_id": "…", "user_id": 123, "limits": { "question_chars": 2000 } }`. Только этот ответ выдаёт исходный токен, при доставке используется TLS. Новая сессия не получает историю старой. Потерянный ответ входа допускает новую пустую сессию; прежняя истечёт сама.

## POST /session/resume — перезагрузка

Bearer и тело `{ "launch_query": "…" }`. Проверить действительность токена, подпись, app/user ID и совпадение канонического launch_digest с исходным запуском сессии. Здесь возраст исходного запуска может превышать 300 секунд, но сессия не должна истечь. Проверить общий допуск. `200`: expires_at, current dialog_id, user_id, limits; новый токен не выдаётся и срок не продлевается.

Несовпадение запуска/пользователя — `401 resume_mismatch`, без истории. Клиент очищает старое состояние и делает новый вход только со свежими параметрами; устаревшие параметры требуют закрыть и заново открыть Mini App. На каждой загрузке данные чата запрашиваются лишь после resume/login. Прямой запуск без проверяемых параметров закрыт даже при наличии сохранённого ID диалога.

## DELETE /session

Bearer; отозвать текущую сессию, закрыть диалоги/отменить незавершённое, `204`. Подписка не нужна. Клиент удаляет токен и отображаемую историю. Повтор с уже отозванным токеном — 401, интерпретируется UI как завершённый выход.

## POST /dialogs — «Новый диалог»

Bearer; тело `{ "dialog_id": "<новый UUID клиента>" }`. ID создаётся до первого POST для безопасного повтора. Под блокировкой сессии закрыть прежний диалог и создать новый с пустым контекстом. `201`: `{ "dialog_id": "…", "state": "active" }`.

Повтор того же ID текущего диалога — `200`, без повторного сброса. ID ранее закрытого диалога — `409 dialog_closed`; он не возобновляется и не закрывает более новый. Коллизия чужого ID — 404. История старого диалога в UI не предлагается; прямой запрос к закрытому диалогу своей сессии возвращает `409 dialog_closed`.

## POST /dialogs/{dialog_id}/requests

Bearer; тело `{ "request_id": "<UUID>", "text": "Вопрос участника" }`.

Проверить 1–2000 Unicode code points до нормализации; пробельный текст отклонить. Сохранять исходный текст для сравнения повторов. Эффективный вопрос формируется сервером из контекста этого диалога по существующей логике; client context не принимается.

При первой регистрации сервер под блокировкой диалога сохраняет context_request_id из pending_request_id в одной транзакции с вопросом и sequence. Повторы не меняют эту зависимость. Перед каждой попыткой, включая первую после очереди, проверить состояние `completed/clarify` сохранённого уточнения и доступность его версий. Недействительная или отсутствующая зависимость даёт invalidated без поиска и вызова модели, даже если чтение истории уже очистило pending-контекст диалога. Её нельзя трактовать как вопрос без уточнения. Effective_query формируется из указанного уточнения при первой попытке; повтор использует ранее зафиксированное значение, не смешивая его с более поздним контекстом.

- Новый ID: короткая регистрация, `202` с representation обращения, state=queued.
- Тот же ID и точный текст: `202` для queued/running; `200` для завершённого/недействительного/отменённого. Нет нового вопроса или продвижения контекста.
- Тот же ID и иной текст: `409 request_conflict`, даже если после нормализации строки совпали.
- Retryable_failed/denied: явный повтор этого POST может поставить ту же запись в очередь, если попытки остаются, доступ есть, диалог активен и более поздний вопрос ещё не принят. Иначе `retry_allowed=false` либо `409 retry_superseded`.
- Другой ID при активной обработке: `409 dialog_busy`, новый вопрос не зарегистрирован.

Если ответ POST потерян, клиент повторяет прежние ID/текст. Изменение вопроса требует нового ID. Повтор после истечения сессии не переносится в новый диалог автоматически.

## GET /dialogs/{dialog_id}/requests/{request_id}

Bearer; `200` с текущим representation. GET никогда не ставит задачу в очередь и не вызывает модель. Для queued/running UI опрашивает раз в 2 секунды; на скрытой вкладке пауза, при возвращении сначала обновление допуска/состояния. Сетевой сбой допускает повтор GET без создания нового запроса.

Просроченное ожидание или попытка переводятся в безопасную временную ошибку при чтении; поздний commit попытки блокируется сменой attempt_id. Предел 180 секунд определяет допустимость результата, а не гарантирует физическое прекращение сетевого вызова. Проверка членства для самого GET сохраняет обычные сроки общей ClubMembers; клиентский сетевой timeout не отменяет серверную обработку.

## GET /dialogs/{dialog_id}/history?after_sequence=0&limit=50

Bearer; limit 1–50. `200`: `{ "dialog_id": "…", "items": [ … ], "next_after_sequence": 50, "has_more": true }`. Порядок sequence возрастающий, один элемент на обращение (вопрос и его состояние/ответ). Полный повтор чтения не создаёт сообщения. Для малого активного чата клиент обновляет известные request ID, не добавляет их повторно.

Перед сериализацией каждой порции повторно проверить допуск и происхождение всех выдаваемых ответов. Недействительные ответы заменить полностью; ответ с частично удалёнными карточками не допускается. Недоступность проверки даёт 503 без порции истории.

Инвалидация ответа-уточнения и сброс pending-полей выполняются под блокировкой его диалога, общей с регистрацией вопросов. Сохранённые context_request_id зависимых обращений остаются неизменными: worker обнаруживает недействительное уточнение по этой связи даже после очистки контекста историей.

## Representation обращения

Общие поля: `dialog_id`, `request_id`, `sequence`, `state`, `operation_id`, `question`, `retry_allowed`. Для completed: `answer: { outcome, text, cards }`. Карточки используют действующие типы `episode/page/letter/document/material/navigation` и поля [контракта 002](../../002-slides-letters-schedule/contracts/search-cards.md), не более трёх. Внутренняя provenance, effective_query и attempt_id наружу не выдаются.

Для queued/running нет answer. Retryable_failed содержит безопасные `error_code/message`, без промежуточных выдержек. Invalidated — нейтральное сообщение «Материалы ответа изменились или недоступны. Выполните новый поиск», cards отсутствуют. Cancelled — «Диалог завершён». Denied виден только после восстановления допуска; при текущем отказе вместо representation возвращается 403.

`operation_id` обращения стабилен; попытки и чтения различаются в telemetry через attempt_no/event. Ошибка до регистрации получает собственный operation ID. Продолжительность каждой попытки фиксируется без текста вопроса.

## Общий поисковый сервис

Внутренний вызов: эффективный вопрос, callback проверки подтверждённого участника, соединение/фабрика БД, клиент AI и необязательный deadline. Возвращает outcome, текст, карточки, provenance и метрики. Сервис не создаёт events, не обновляет транспортный контекст и не отправляет сообщения.

Сохранить `find_candidates → decide → explanations → build_cards`, действующие пределы повторной проверки версий и резервные пояснения. Callback вызывается до поиска/векторизации, перед передачей выдержек генератору и перед результатом. Версии выдержек повторно проверяются до внешней передачи и перед выдачей. Для вариантов уточнения Decision возвращает происхождение выбранных названий. Не вводить новые пороги ранжирования.

Старый `/api/search` остаётся внутренним и сохраняет HTTP/JSON-контракт, `events`, `random_id` и доставку. Общий singleton допуска создаётся в `create_app`, передаётся обоим каналам; состояние оповещения `club` сохраняется общим.
