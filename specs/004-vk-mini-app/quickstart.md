# Проверка 004 на текущем стенде

**Дата:** 2026-11-23. Это инструкция для будущей реализации. Новые команды frontend, gateway и тесты Mini App станут исполняемыми после реализации; ниже они не описываются как уже выполненные.

## 0. Проверить интеграцию VK до завершения планирования

**Статус: документация и изолированная проба подготовлены; живая часть выполнена частично.** Владелец открыл страницу Mini App и контрольные ссылки, но установка без модерации в его интерфейсе недоступна. 2026-11-23 он согласовал продолжение реализации на test-db/UI и перенос запуска с плитки, модерации и живых SC на целевой сервер (R13 research.md). Это не подтверждение настоящей подписи, iframe на обоих устройствах или SC-01. Защищённый ключ остаётся на серверной стороне, реальные параметры запуска не записываются в логи или протокол.

Нужны зарегистрированное Mini App, возможность задать его HTTPS-адрес, серверный доступ к защищённому ключу и контрольная учётная запись с доступом к выбранным источникам. Проверить:

Для первого опыта владелец разрешил своё другое сообщество, где у него есть административный доступ. Зафиксировать его ID и явно помечать эти результаты как пробу тестового сообщества. Подписка и каталог по-прежнему относятся к «Экопрофи»; роль администратора тестовой группы не даёт исключения из проверки подписки. Плитка и полная цепочка в «Экопрофи» остаются обязательными для финальной приёмки.

Подготовка регистрации пользователем:

- Открыть [портал VK для разработчиков](https://dev.vk.com/), войти под аккаунтом владельца тестового сообщества, открыть список приложений и выбрать создание приложения. Такой порядок описан в [официальном учебном проекте VK](https://github.com/VKCOM/vk-mini-apps-course-frontend#-запуск-мини-приложения).
- Если доступен выбор типа, выбрать «Мини-приложение / VK Mini Apps». Рабочее название для пробы — «Найти лекцию — тест». Пройти регистрацию, включая подтверждения, которые VK требует от владельца аккаунта.
- Передать исполнителю app ID либо ссылку приложения и ссылку/ID тестового сообщества. Защищённый ключ не отправлять в чат: после подготовки пробы сохранить его в локальных серверных настройках по инструкции исполнителя.
- HTTPS-адрес не придумывать: исполнитель предоставит его после подготовки пробы. Если мастер требует адрес до создания приложения, остановиться на этом поле и сообщить его название; способ регистрации уточняется по фактическому интерфейсу.
- Пока портал не отдаёт исполнителю основной текст [Подписи параметров запуска](https://dev.vk.ru/ru/mini-apps/development/launch-params-sign), открыть её в обычном браузере и скопировать сюда только основной текст с примерами (можно через «Выделить всё» → «Копировать» → вставить в сообщение). Не копировать защищённый ключ, cookies, токены или параметры своего запуска. Это нужно для завершения T001.
- Подключение к тестовому сообществу и настройку плитки выполнить после готовности страницы пробы. Для финального размещения в «Экопрофи» потребуется участие пользователя с подтверждёнными правами управления; имеющиеся API-ключи сами по себе не подтверждают возможность создания плитки.

Проверки после подготовки:

1. Актуальную официальную документацию VK о подписи и полях запуска, времени запуска, Bridge и открытии ссылок. Зафиксировать страницы и дату сверки; отдельно обозначить сроки 300/+60 секунд как политику проекта. Если документация недоступна, архивный пример не закрывает эту проверку.
2. На телефоне и ПК — доступность выбранного HTTPS-входа из VK, инициализацию Bridge и успешную серверную проверку настоящего запуска. Изменение подписанного параметра даёт отказ. Проверить получение исходных параметров после перезагрузки и нового открытия, чтобы подтвердить правила login/resume и возраста запуска.
3. На обоих типах устройств — открытие стабильных ссылок контрольного видео, презентации и письма. Зафиксировать фактическое поведение таймкода/страницы и сохранение видимых координат, когда точный переход не поддерживается.

Результаты записать в research.md: дата, ОС/клиент VK, роль, app ID без секрета, контрольный материал, ожидаемый/наблюдаемый результат и ограничение вывода. Не сохранять launch query, sign, токены или адресную строку на снимках. По результатам скорректировать контракты. Этап закрывается только при наличии документации и наблюдений с обоих типов устройств; до этого планирование остаётся открытым. Эти пробы подтверждают техническую возможность интеграции, а полная цепочка SC-01 проверяется после реализации по разделам ниже.

## 1. Подготовить проверяемую сборку

Требуются Docker Desktop текущего проекта, Node/npm совместимых закреплённых версий, реализованные документы [плана](plan.md), зарегистрированное Mini App с возможностью настройки адреса и установки в сообществе. Для основного входа нужен постоянный Cloudflare Tunnel и его токен; cloudflared запускается сервисом Compose. Белый IP, входящий 443 и Origin CA не требуются. Защищённый ключ хранится локально в `.env`, только в окружении bot; значения не вставляются в протокол.

Перед рабочей миграцией сохранить резервную копию текущей БД существующим порядком (как в 003): `docker compose exec -T db pg_dump -U ecoprofi_owner ecoprofi > out/backup-before-004.sql`, затем убедиться, что файл не пуст. Каталог `out/` в git не попадает. Миграцию 004 сначала проверить в изолированной test-db, включая повторное применение и права ролей. Не выполнять `down -v` и не подменять рабочий каталог тестовым корпусом.

Планируемые проверки из корня проекта после реализации:

```powershell
docker compose --profile test run --rm --build tests
npm --prefix mini-app ci
npm --prefix mini-app run typecheck
npm --prefix mini-app test -- --run
npm --prefix mini-app run build
npm --prefix mini-app run test:e2e
```

Первый запуск e2e требует `npx --prefix mini-app playwright install chromium`. Проверка шлюза выполняется против отдельного контейнера без bot — команды в docstring `tests/integration/test_miniapp_gateway.py`; внутри profile test эти 6 тестов пропускаются. После изменения уже применённой к test-db миграции test-db нужно пересоздать (`docker compose --profile test up -d --force-recreate test-db`): она в tmpfs и не затрагивает рабочий том.

`test:e2e` должен сам поднимать изолированный frontend/API stub и завершать их; подписи тестовых запусков используют только искусственный секрет. Для интеграционных тестов нужен profile test с TEST_*_DATABASE_URL; пропущенные из-за отсутствия БД тесты не считать пройденными. Протокол содержит команды, exit code, числа passed/failed/skipped и причину пропусков.

Регрессия охватывает test_club, test_access, test_telemetry, test_alerts_api, test_search_outcomes, test_delivery, test_audience, test_catalog_search и весь существующий набор. Отдельно проверить отказ индексатору в чтении таблиц Mini App и отсутствие изменений каталога миграцией.

## 2. Поднять вход текущего ПК

После реализации build-target `miniapp-gateway` и сервиса `miniapp-gateway` под Compose profile `miniapp` сначала собрать образы, затем применить миграцию именно новым образом bot и проверить её регистрацию в рабочей БД. Сборка tests использует другой target и не обновляет образ bot. При ошибке любого шага не запускать новую версию; устранить причину и повторить проверку.

```powershell
docker compose --profile miniapp build bot miniapp-gateway
if ($LASTEXITCODE -ne 0) { throw 'Сборка Mini App не выполнена' }
docker compose run --rm bot python -m ecoprofi.bot.migrate
if ($LASTEXITCODE -ne 0) { throw 'Миграция Mini App не выполнена' }
$miniappMigration = docker compose exec -T db psql -U ecoprofi_owner -d ecoprofi -tAc "SELECT name FROM schema_migrations WHERE name = '004_miniapp.sql';"
if ($LASTEXITCODE -ne 0 -or "$miniappMigration".Trim() -ne '004_miniapp.sql') { throw 'Миграция 004 не подтверждена' }
docker compose --profile miniapp up -d bot miniapp-gateway
if ($LASTEXITCODE -ne 0) { throw 'Запуск Mini App не выполнен' }
```

**Постоянный адрес (R15, 2026-11-24):** `https://miniapp.bot-alimony.ru` через постоянный Cloudflare Tunnel. Стенд остаётся на текущем ПК. Файл токена получен, коннектор запущен, но соединение до Cloudflare не устанавливается (QUIC timeout / HTTP/2 TLS EOF); внешний адрес вернул 522. Подтверждение маршрута и успешного внешнего входа остаётся открытым. **2026-11-24 (R16):** туннель из региона не работает (Error 1033, TLS EOF), внешний вход переносится на VPS — см. `specs/005-vps-migration/tasks.md`. Раздел ниже сохранён как история.

Однократная настройка:

1. Зона `bot-alimony.ru` в Cloudflare должна быть **Active**.
2. Создать remotely-managed Cloudflared Tunnel `ecoprofi-miniapp` в кабинете Cloudflare.
3. Сохранить только токен туннеля в `deploy/secrets/cloudflared-token.txt` (одна строка, UTF-8 без BOM). Файл исключён из Git и build context; не вставлять токен в чат, командную строку или `.env`.
4. Добавить published application route: `miniapp.bot-alimony.ru` → `http://127.0.0.1:8080`. Cloudflare создаёт CNAME на `<UUID>.cfargotunnel.com`. При конфликте убрать только прежнюю A/AAAA `miniapp`, указывающую на ПК. Не включать отдельную авторизацию Cloudflare Access перед VK Mini App.
5. Убрать проброс NAT 443, если он был настроен специально для Mini App. Origin CA больше не подключается. `MINIAPP_PUBLIC_ORIGIN=https://miniapp.bot-alimony.ru` остаётся прежним.

`miniapp-tunnel` использует network namespace шлюза, поэтому `127.0.0.1:8080` доступен обоим контейнерам. nginx доверяет `CF-Connecting-IP` только от loopback. Запросы соседних контейнеров и через опубликованный Docker-порт не получают этого доверия. Это сохраняет лимит по адресу участника, а не общему адресу коннектора.

```powershell
docker compose --profile miniapp build miniapp-gateway
docker compose --profile miniapp run --rm --no-deps --entrypoint nginx miniapp-gateway -t
docker compose --profile miniapp --profile tunnel up -d miniapp-gateway miniapp-tunnel
docker compose --profile miniapp --profile tunnel ps
curl.exe -sSI https://miniapp.bot-alimony.ru/
```

Ожидается Healthy в Cloudflare, HTTP 200 и CSP с frame-ancestors VK. Обновлять и пересоздавать gateway/tunnel совместно указанной командой `up`; зависимость с `restart: true` обновляет сетевое подключение коннектора после пересоздания шлюза. `restart: unless-stopped` поднимает контейнеры при запуске Docker Desktop; ПК и Docker должны работать. Подробная инструкция для владельца: `Инструкции для меня по домену.txt` в корне проекта.

Quick Tunnel оставлен только для изолированной пробы `tools/miniapp-probe`; постоянный стенд использует именованный туннель. `deploy/cloudflared-miniapp.example.yml` — альтернативный шаблон локально управляемого туннеля, он не используется сервисом с токеном.

Официальные источники: [создание туннеля](https://developers.cloudflare.com/tunnel/get-started/), [token-file](https://developers.cloudflare.com/tunnel/reference/run-parameters/#token-file).

Проверить публичный allowlist: статика открывается, `/api/miniapp/v1/session` без подписи отказывает, `/api/search`, `/api/delivered`, `/api/alerts/pending`, `/docs`, `/openapi.json` недоступны. Положительная проверка служебного ключа выполняется только внутри Compose; ключ не передаётся через туннель.

В настройках зарегистрированного Mini App заменить адрес минимальной пробы этапа 0 на HTTPS-адрес полной сборки, проверить нужные платформы испытаний и установить приложение в сообщество «Экопрофи» с плиткой «Найти лекцию». Настройки полной сборки и размещение плитки выполняются на этом этапе; их выполнение пока не подтверждено. Если интерфейс портала или способ установки отличается от ожиданий, записать наблюдение и обновить инструкцию.

Если туннель недоступен из сети участника, живая проверка остаётся открытой. Не заменять её успехом localhost и не объявлять 004 принятой. После смены туннеля обновить origin и адрес Mini App, затем заново открыть приложение; старый origin не поддерживается.

## 3. Проверить вход и изоляцию

Подготовить две разные учётные записи подписчиков для SC-03, неподписчика и утверждённое исключение. Контрольные материалы брать из уже опубликованного каталога: эпизод, презентация, письмо, запись без текста. Не менять подписку или публикации реальных пользователей ради автоматического теста — отзыв и смена версий воспроизводятся в test-db, живые наблюдения записываются только если действительно сделаны.

- На телефоне и ПК открыть плитку, подтвердить отсутствие ручного ввода ID, пароля и служебного токена. Зафиксировать ОС/клиент VK, дату, app ID без секретов, роль и исход.
- Неподписчик получает только пояснение/ссылку клуба. Исключение получает доступ без подписки. Недоступность проверки моделируется в test-db; живой сбой не объявляется наблюдавшимся по этому тесту.
- Подменить в синтетической подписи app/user/ts/sign, добавить дубли ключей, пустые/неверные значения, проверить кодировку `+`, `%20`, `%2B` и сохранение пустых параметров. Модель не вызывается при отказе.
- Два участника ведут по два независимых запуска: разные вопросы/уточнения, чужие dialog/request ID и bearer, новый диалог во время ответа. Проверить, что запоздалый ответ не меняет новый экран.
- Перезагрузить вкладку с действующей сессией; она восстанавливает свой диалог через resume. Перейти к другой учётной записи и проверить отсутствие прежней истории. Подменённые часы теста проверяют границы 300 секунд, +60 секунд и 8 часов; ожидать восемь часов вручную не требуется.

## 4. Проверить материалы и повторы

- Вопрос → уточнение → ответ → источник на телефоне и ПК. Для эпизода сверить интервал в плеере, для презентации страницу, для письма реквизиты с оригиналом. Запись без субтитров выдаётся целиком. Зафиксировать фактическое поведение точного перехода, а не только HTTP 200 ссылки.
- Пустой текст, пробелы, 1/2000/2001 символ, в том числе Unicode вне BMP. Неверный текст не запускает поиск и остаётся редактируемым.
- Двойной клик, два конкурентных POST одного ID, тот же ID с другим текстом, второй вопрос занятого диалога, разрыв после регистрации/после commit ответа. Один вопрос и один завершённый ответ; контекст применяется один раз.
- GET статуса и истории не вызывает AI. Отзыв допуска по окончании TTL закрывает повторы/историю. Источник снят с публикации/сменил аудиторию/версию: пропадает весь старый ответ, включая названия вариантов уточнения. Эти изменения проверять в изолированной БД.
- На тестовой очереди проверить срок допустимости результата, переполнение, лимит попыток, повтор старой ошибки после нового вопроса. Искусственно задержать HTTP/проверку членства за пределом срока: поздний результат не сохраняется; освобождение потока ровно через 180 секунд не является обещанием. Затем прервать worker после claim и перед commit: восстановление даёт безопасный повтор, старый attempt не коммитится. Отдельно снять источник уточнения, пока первый вопрос на его основе ожидает в очереди: попытка не передаёт effective_query модели.
- Отдельная проверка гонки с историей: получить уточнение A с источником, приостановить worker до claim, зарегистрировать ответ B и убедиться, что B.context_request_id=A уже сохранён. Снять источник A, прочитать историю до её инвалидации A и сброса pending-полей, затем разрешить worker продолжить. B должен стать invalidated без вызовов поиска/AI, а его context_request_id остаться A; повтор того же B не создаёт новую попытку. Контрольный вариант с доступным A использует его контекст ровно один раз. Проверить также конкурентную регистрацию B и инвалидацию A: транзакции сериализуются общей блокировкой диалога, зависимость не теряется после её фиксации.

## 5. Остановка и диагностика

На текущем стенде остановить bot при открытом чате: видна ошибка, не «материал не найден». Запустить обратно и проверить восстановление/повтор. Остановить туннель и отдельно открыть приложение заново: ошибка VK/браузера фиксируется как недоступность входа. Перезапуск туннеля может изменить адрес, тогда повторить настройку origin.

В тестовой среде ускорить часы, проверить немедленный отказ истёкшей сессии и физическую очистку её диалогов/вопросов/ответов после запуска или очередного интервала очистки. Проверить каскадное удаление при работающей попытке и безопасное отбрасывание позднего результата.

По operation ID найти исход, длительность попытки, источники/версии и channel=miniapp. Контрольные искусственные секреты не должны появляться в frontend build, stdout сервисов, access/debug logs и протоколе. Отдельно проверить ошибки валидации: они не отражают launch_query/bearer. Снимки экрана не содержат адресную строку с подписью; тексты закрытых материалов в отчёт не копируются без необходимости.
