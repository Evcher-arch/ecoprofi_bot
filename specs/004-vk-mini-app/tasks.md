## Зависимости и порядок выполнения

```text
T001 → T002 → T003 → T004 → {T005, T006}
    → основание T007–T016
    → US1 T017–T028
    → US2 T029–T042
    → US3 T043–T055
    → общая приёмка T056–T060
```

Внутри фазы порядок по ID действует по умолчанию. Исключения для `[P]` приведены ниже. Тестовые задачи задают ожидаемое поведение до соответствующей реализации; их положительный запуск проводится на контрольной точке фазы. T012–T013 меняют один файл и последовательны; все изменения repository.py, api.py и worker.py также выполняются последовательно.

| Работа | Предпосылка / результат |
| --- | --- |
| T001–T004 | Закрывают этап 0 нового входа. Отсутствие живой пробы не закрывается фактом работы старого бота. |
| T007 и T011 | После подготовки можно одновременно писать проверки сервиса и миграции; разные файлы. |
| T008 → T009 → T010 | Один runtime и общий поиск, затем сохранённый старый контракт. |
| T012 → T013 → T014 → T016 | Схема, фикстуры, проверка основания; рабочую БД на этом этапе не менять. |
| US1 | Зависит от основания; исполнима и проверяема без US2/US3. |
| US2 | Использует подтверждённые сессии US1; её тесты не требуют завершённой обработки сбоев US3. |
| US3 | Расширяет работающий путь US2; проверки отказов обязательны до итоговой приёмки. |
| T028, T042, T055, T058–T059 | Требуют подготовленных сборок, HTTPS и нужных ролей; повторное развёртывание оправдано изменением сборки между историями. |
| T060 | Только после фактов T056–T059 и решения владельца; матрица сама не является прохождением критериев. |

### Возможности параллельной работы

- Подготовка: после T004 — T005 (frontend) и T006 (матрица); после неё — T007 и T011 (разные тесты).
- US1: T017, T018, T019 — разные наборы тестов; после T022 — T023 (клиент входа) и T025 (nginx). T024 ждёт T023, T026 ждёт T024–T025.
- US2: T029, T030, T031 — разные проверки; после T036 — T037 (карточки) и T038 (состояние чата). T039 ждёт оба результата.
- US3: после US2 — T043, T044, T045, T046 в разных файлах. Реализация T047–T053 последовательна из-за общих repository/worker/API.

Эти возможности описывают независимость работ; автоматический запуск дополнительных агентов не требуется.
