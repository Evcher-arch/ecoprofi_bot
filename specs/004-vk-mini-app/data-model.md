## miniapp_session

| Поле | Тип / ограничение | Смысл |
| --- | --- | --- |
| id | UUID PK | Внутренний идентификатор сессии. |
| token_hash | bytea UNIQUE NOT NULL | SHA-256 случайного 256-битного bearer; исходный токен не хранится. |
| app_id, user_id | bigint > 0 | Значения, подтверждённые подписью запуска. |
| launch_digest | bytea NOT NULL | SHA-256 канонических подписанных параметров и подписи; для возобновления исходного запуска. Не исходная query. |
| launch_ts | timestamptz NOT NULL | Подписанное время запуска. |
| created_at, expires_at | timestamptz NOT NULL | Абсолютное истечение через 8 часов; expires_at > created_at. |
| revoked_at | timestamptz NULL | Явное завершение сессии. |
| current_dialog_id | UUID NULL | Указатель текущего диалога; составной FK гарантирует ту же сессию. |

Здесь нет признака «подписчик» или бессрочного разрешения. Действительность токена, срок, ожидаемый app ID и допуск проверяются при обращении. Индексы: token_hash, expires_at. Не создавать FK на `participant` или `test_group`.

## miniapp_dialog

| Поле | Тип / ограничение | Смысл |
| --- | --- | --- |
| id | UUID PK | Отдельный диалог, не peer ID VK. |
| session_id | UUID FK → session ON DELETE CASCADE | Владелец определяется через сессию. |
| state | active / closed | Закрытый диалог не принимает новые вопросы и не возобновляется. |
| created_at, closed_at | timestamptz | Время создания/закрытия. |
| next_sequence | bigint > 0 | Номер следующего вопроса. |
| pending_query | text NULL | Контекст существующего механизма уточнения, не вся переписка. |
| pending_request_id | UUID NULL | Ответ-уточнение, от которого зависит контекст; FK вместе с dialog_id. |

UNIQUE `(session_id, id)` для составной ссылки session.current_dialog_id; UNIQUE partial `(session_id) WHERE state='active'`. Создание сессии и первого диалога — одна транзакция; циклическая ссылка current_dialog заполняется после вставки диалога. Удаление каскадом реализовать без взаимной блокировки FK (ссылка на текущий диалог отложенная до commit).

Новый диалог создаётся атомарно под блокировкой сессии: закрыть прежний, очистить его pending-поля, отменить ожидающие/выполняемые запросы, создать новый и обновить current_dialog_id. Сам по себе UUID не даёт доступа. На сессию максимум 20 созданных диалогов; после лимита предлагается новый вход, без удаления записей идемпотентности действующей сессии.

## miniapp_request

| Поле | Тип / ограничение | Смысл |
| --- | --- | --- |
| dialog_id, request_id | UUID, составной PK | Клиентский UUID обращения в конкретном диалоге. |
| sequence | bigint > 0 | UNIQUE `(dialog_id, sequence)`, порядок истории. |
| original_text | text NOT NULL | Исходная строка; длина 1–2000 code points, не только пробелы. |
| text_digest | bytea NOT NULL | SHA-256 точного исходного UTF-8; дополнительно сравнивается строка. |
| effective_query | text NULL | Фиксируется при первой попытке после проверки сохранённой зависимости; исходный текст дополняется effective_query уточнения по context_request_id, затем нормализуется/обрезается по действующей логике, максимум 2000 символов. |
| context_request_id | UUID NULL | Неизменная зависимость: копия pending_request_id под блокировкой диалога при первой регистрации обращения. NULL только если тогда контекста не было; проверяется при первой и повторных попытках. |
| state | enum-like text CHECK | Состояния ниже. |
| outcome | found / clarify / empty / NULL | Поисковый исход только у completed. |
| result | jsonb NULL | Текст и карточки; только законченный ответ, без параметров входа. |
| provenance | jsonb NOT NULL | Массив уникальных пар material_id/version_id для всего ответа, включая варианты уточнения. |
| operation_id | text NOT NULL | Существующий формат telemetry.new_operation_id; стабилен у обращения. |
| attempt_id | UUID NULL | Меняется при новой попытке и восстановлении; защита от позднего commit. |
| attempt_no | integer ≥ 0 | Число попыток, максимум 3 на request ID. |
| error_code | text NULL | Безопасный код, не текст исключения. |
| queued_at, started_at, finished_at, created_at | timestamptz | Очередь, длительность и сроки. |

FK dialog_id ON DELETE CASCADE; context_request_id и pending_request_id ограничены тем же dialog_id. Контекстные ссылки допускают NULL и откладываются до commit при каскадном удалении. Происхождение хранить значениями, без каскадного FK к материалу: после удаления источника должна сохраняться возможность распознать недействительный ответ.

При ненулевом context_request_id зависимость должна указывать на более раннее обращение того же диалога, остающееся `completed/clarify`, с доступными версиями источников. Проверяется и состояние, и provenance: пустая карта у уже invalidated-уточнения не означает допустимость. Если зависимость недействительна или отсутствует, новый вопрос становится invalidated до поиска/AI; обработка без контекста запрещена. Сброс dialog.pending_* не меняет context_request_id зарегистрированных обращений. После успешной проверки effective_query строится из неизменного effective_query указанного уточнения и нормализованного original_text нового вопроса; текущее dialog.pending_query для этого не читается. Повтор использует уже сохранённый effective_query с новой проверкой той же зависимости.

Индексы: `(state, queued_at)` для очереди, UNIQUE partial `(dialog_id) WHERE state IN ('queued','running')`. Не более 200 обращений на сессию; повтор уже известного ID разрешается и после лимита. Лимиты 20/200/32 — ограничения ресурсов стенда, не правила подписки. Проверять лимит общей очереди атомарно через короткую transaction-level advisory lock; отмена и завершение освобождают место.

## Состояния и переходы

| Из | В | Условие |
| --- | --- | --- |
| отсутствует | queued | Подтверждены сессия/допуск/владение, текст и лимиты; вставка, sequence и снимок context_request_id атомарны. |
| queued | running | Worker владеет singleton lock, очередь не просрочена; новая попытка и attempt_id зафиксированы. |
| queued | retryable_failed | Ожидание больше 180 секунд; error_code=queue_timeout. |
| running | completed | Сервис завершён, дедлайн не истёк, допуск/версии актуальны, attempt совпал; ответ и контекст одним commit. |
| running | retryable_failed | Временная ошибка, дедлайн или обнаруженное при восстановлении прерывание. |
| queued/running/retryable_failed/denied | invalidated | Источник использованного уточнения недействителен; без нового поиска и передачи effective_query модели. |
| queued/running | denied | Общая проверка вернула отсутствие подписки; нет result/provenance, контекст этой попыткой не продвигается. |
| retryable_failed/denied | queued | Явный POST того же текста/ID, доступ восстановлен, диалог активен, нет более позднего обращения, лимит попыток не достигнут. |
| completed | invalidated | Любой источник перестал соответствовать visible_versions; очистить весь result и связанный pending-контекст. |
| queued/running/retryable_failed/denied | cancelled | Закрыт диалог/сессия; поздняя попытка больше не коммитится. |
| любое | удалено | Истекла сессия и наступила физическая очистка. |

`completed`, `invalidated`, `cancelled` не возвращаются в обработку. Исчерпанные попытки дают `retry_allowed=false`; новый вопрос требует нового request ID. Если после ошибки принят более поздний вопрос, повтор старой ошибки не переигрывает контекст: вернуть `409 retry_superseded`. Перед каждой попыткой с контекстом, в том числе первой после очереди, проверить источник уточнения до формирования/использования effective_query; если он недействителен — `invalidated` с предложением нового поиска, без старого текста ответа.

## Транзакции и восстановление

1. Владение всегда проверяется JOIN через session_id из bearer, а не по request ID отдельно. Существование чужой записи наружу не раскрывается.
2. При регистрации сначала найти существующий ID под блокировкой диалога. Совпадение текста проверяется до проверки busy/лимита, чтобы повтор не стал новым вопросом. Только для нового ID в этой же транзакции скопировать pending_request_id в context_request_id и назначить sequence; повтор не перезаписывает зависимость. Инвалидация уточнения и очистка pending-полей при чтении истории используют ту же блокировку диалога; порядок блокировок общий: диалог → его обращения. Сеть выполняется вне этих блокировок.
3. Worker удерживает singleton advisory lock отдельным соединением; при утрате соединения прекращает новые claims и выдачу результатов. Новый владелец lock меняет attempt_id прежних running перед их повтором. Старый процесс не сможет записать ответ при несовпадении attempt.
4. В commit результата повторно проверяются state, attempt_id, срок/отзыв сессии, active/current dialog и действительность сохранённой зависимости уточнения. Pending-контекст диалога продвигается только здесь; context_request_id самого обращения уже зафиксирован при регистрации. Ошибка или падение не продвигают контекст.
5. Чтения каталога и вызовы сети не держат row lock диалога. Итоговая проверка опубликованных версий делается в короткой транзакции перед записью; выдача снова проверяет версии, поэтому изменение после commit не раскрывает старый ответ.
6. На старте worker очищает истёкшее и восстанавливает interrupted. Неистёкшие queued сохраняют порядок, просроченные переходят в ошибку. Удаление сессии делает запоздалый commit пустым.
7. 180 секунд — срок допустимости результата, а не обещание прервать синхронный HTTP или ожидание общей ClubMembers. Worker, чтение статуса/истории и POST повтора проверяют время; просроченное running атомарно становится retryable_failed со сменой attempt_id. Поздний результат не коммитится. Постановка повтора в очередь не запускает параллельно второй вызов того же worker. Отдельные maintenance-проверки истечения/очистки не должны зависеть от окончания поискового вызова: выполнять их в периодическом обслуживании процесса bot отдельно от рабочего потока поиска.

## Права, очистка и совместимость

Новые таблицы доступны на SELECT/INSERT/UPDATE/DELETE роли `ecoprofi_bot`; `ecoprofi_indexer` прав не получает. Каталог и очередь индексатора не меняются. Миграция выполняется существующим migrate под владельцем схемы, повторный запуск без изменений. Расширить сброс test-db новыми таблицами; убедиться, что старые тесты не наследуют Mini App данные.

Откат приложения: отключить маршруты/worker и gateway, оставить добавочные таблицы закрытыми. Удаление таблиц для отката не требуется; существующий bot продолжает работать. Рабочая миграция — после резервной копии; на этапе планирования она не запускается.

Истечение проверяется независимо от очистки. Физическая очистка в первые 15 минут работы после истечения либо сразу после запуска, если срок истёк при остановке. В operational log остаются только разрешённые технические поля; тексты диалога и токены туда не переносить.
