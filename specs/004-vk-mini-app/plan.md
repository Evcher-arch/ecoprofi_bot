
# План реализации 004: VK Mini App «Найти лекцию»

**Дата:** 2026-11-23. **Функция:** `004-vk-mini-app`. **Git-ветка:** `master`.
**Основание:** [spec.md](spec.md), конституция v1.1.0. **Статус:** технический проект подготовлен; планирование не завершено до проверки VK на этапе 0. Реализация и живая приёмка не выполнены.

Активная функция задана в `.specify/feature.json`. Значение `BRANCH=004-vk-mini-app` из setup-plan обозначает функцию; фактическая Git-ветка проверена отдельно. Переключения ветки и коммита при планировании не было.

## Результат и подход

Добавить личный чат Mini App поверх текущего каталога и поиска. Интерфейс React/TypeScript с VKUI и VK Bridge размещается за локальным шлюзом вместе с пользовательским API. Внешний HTTPS ведёт к шлюзу на текущем ПК через постоянный Cloudflare Tunnel (решение R15 research.md); cloudflared запускается в Compose. База, bot и индексатор остаются на месте. Доступность адреса из сетей испытателей проверяется до испытаний с реальными данными.

В существующем процессе bot добавить маршруты `/api/miniapp/v1/*`, выделить общий поисковый сервис и общую проверку членства. Сессии, диалоги и обращения Mini App хранить в отдельных таблицах PostgreSQL. Существующий `events` и контракт Bots Long Poll сохраняются. Новый канал не отправляет сообщения в VK.

Вход проверяет подпись запуска, ожидаемый ID приложения, пользователя и возраст запуска; далее выдаётся ограниченный по сроку непрозрачный bearer-токен. Подписка проверяется общей `ClubMembers` на каждом обращении и перед выдачей результата; срок сессии не продлевает допуск по подписке.

## Границы компонентов

1. **mini-app/**: запуск Bridge, экран допуска, вопрос, история текущего диалога, карточки и ошибки. Ответы показываются текстом, без исполнения HTML. Ссылки открываются по нажатию, координаты видны отдельно.
2. **gateway**: статика и только `/api/miniapp/v1/`. Остальные `/api/*`, `/docs`, `/openapi.json` и неизвестные пути отклоняются; fallback на HTML не скрывает ошибку API. Порт bot наружу не публикуется.
3. **miniapp router**: запуск/сессия/владелец, общий допуск, приём обращения, безопасная история. `user_id`, `group_id`, `peer_id` от клиента не служат полномочиями.
4. **runtime и search service**: единственная `ClubMembers` процесса, существующие аудитории, поиск и карточки. Вынести управление причиной `club` из замыкания `create_app`; успешный запрос исключения не закрывает сбой VK. Разделить проверку доверенного тестового канала и общий допуск подтверждённого участника.
5. **Mini App worker**: очередь, общий сервис, атомарный результат. Не использует `event`, `dialog_context`, `random_id`, `/api/delivered` или `messages.send`.

Прямой вызов нынешнего `api.answer()` из Mini App не подходит: `resolve_access()` привязан к `test_group` и `peer_id == user_id`, а `events` смешает независимые сессии одного пользователя. Общий сервис получает эффективный вопрос и callback допуска; транспортные обёртки управляют своими контекстами отдельно.

## Очередь, повторы и восстановление

- POST создаёт обращение с клиентским UUID короткой транзакцией и отвечает `202`. В диалоге допускается одно `queued/running`; другой вопрос получает `409 dialog_busy`. UI отключает отправку до исхода текущего вопроса. Диалоги ожидают общего обработчика FIFO.
- При первой регистрации под блокировкой диалога сохранить `context_request_id` из текущего `pending_request_id` вместе с обращением и sequence. NULL означает отсутствие контекста именно в момент регистрации. Эта зависимость неизменна при повторах и очистке pending-полей; effective_query формируется при первой попытке из сохранённой зависимости, а не из текущего состояния диалога.
- Тот же UUID и исходный текст возвращают ту же запись. Изменённый текст — `409 request_conflict`. Повтор готового ответа не запускает модель и не меняет контекст. Повтор временной ошибки явно переводит ту же запись в очередь.
- Один worker владеет session-level advisory lock на отдельном autocommit-соединении. Второй не начинает обработку. Порядок: singleton lock → восстановление незавершённых попыток → очередь. На стенде один процесс uvicorn, без `--workers` и `--reload`.
- Claim, сохранение и очистка — короткие транзакции; блокировка диалога не держится во время HTTP. При текущем `autocommit=False` явно завершать чтение, не полагаться на вложенный `conn.transaction()` как на commit.
- Ответ и продвижение контекста сохраняются атомарно при совпадении `attempt_id`, активных сессии/диалога и состояния `running`. После падения старое `running` получает `retryable_failed/interrupted`, attempt меняется. Поздний результат старой попытки отбрасывается.
- Повтор вычисления после падения до commit возможен; однократный вызов модели не обещается. В чате один вопрос и максимум один завершённый ответ по request ID.
- Дедлайн проверяется до и после внешних этапов и перед commit; для вызовов AI timeout каждой сетевой стадии ограничен 30 секундами и остатком бюджета, SQL statement timeout также ограничен остатком. Это не общий timeout httpx и не прерывание ожидания блокировки/постраничного чтения общей ClubMembers. Поздний результат отбрасывается. GET статуса или POST повтора атомарно переводит просроченную попытку в временную ошибку со сменой attempt_id; не ждёт завершения этой попытки для определения её исхода. Физически выполняющийся вызов может закончиться позднее, поэтому очередь не обещает освобождение worker ровно через 180 секунд. Новый claim выполняется только после окончания прежнего вызова либо восстановления worker. Текущая политика подписки не меняется ради этого тайм-аута.
- Истечение не превращается в `empty`. Резервное пояснение при обычном сбое генерации сохраняется, если дедлайн допустимости ещё не исчерпан. Чтение просроченной очереди также фиксирует queue_timeout вместо бессрочного ожидания; GET не запускает новую попытку.
- «Новый диалог» закрывает предыдущий, отменяет ожидающее обращение и очищает контекст. Выполняемый HTTP не обязан физически прерываться, но его результат не меняет новый диалог. Клиент проверяет dialog ID перед обновлением экрана.

## Сохранённые ответы и доступ

Результат содержит внутреннюю карту `(material_id, version_id)` всех использованных источников. Она нужна и для названий лекций в уточнении. Дополнить `Decision` происхождением вариантов без изменения ранжирования.

Перед историей, повтором и выдачей ответа проверить сессию, владельца, подписку и `visible_versions`. При недоступности любой версии весь ответ становится `invalidated`: карточки, выдержки, пояснения и названия удаляются из сохраняемого результата; остаётся сообщение о новом поиске. Связанный контекст уточнения сбрасывается. Для `empty` и общего уточнения без названий карта может быть пустой. История не запускает скрытый новый поиск.

Перед каждой попыткой, включая первую после ожидания очереди, прочитать уточнение по сохранённому `context_request_id`: оно должно оставаться `completed/clarify`, а его версии — доступными. Проверка выполняется до формирования/использования effective_query. Отсутствующая или недействительная зависимость переводит обращение в invalidated без поиска и передачи текста модели; её нельзя заменить пустым контекстом. Сброс pending-полей при чтении истории не обнуляет `context_request_id` уже зарегистрированных вопросов. Регистрация и сброс контекста сериализуются блокировкой одного диалога.

Отказ допуска возвращается до истории, включая вопросы участника. Уже показанный текст удалённо не отзывается; после отказа UI очищает отображаемую историю и предлагает восстановить доступ.

## Незакрытое условие планирования и зависимости живых проб

Нужны Mini App, его ID/защищённый ключ на backend, возможность настроить адрес и плитку, учётные записи разных ролей, доступный из их сетей HTTPS-вход. Эти ресурсы при планировании не создавались; секреты не запрашивались.

По уточнению владельца приложение ещё не зарегистрировано; первую пробу этапа 0 можно выполнить в другом его сообществе, где у него есть административный доступ. Это проверка нового канала, а не перенос подписки: общий допуск продолжает использовать клуб «Экопрофи», роль в тестовом сообществе исключением не является. Финальная плитка и SC-01 по-прежнему проверяются в «Экопрофи»; для её размещения предстоит обеспечить действия пользователя с правами управления. Ключи API управления/сообщений не засчитываются как подтверждение такой возможности. Подробности и инструкция регистрации — R10 research.md и раздел 0 quickstart.md.

Портал документации VK не открылся через средство исследования; алгоритм подписи сверён с официальным архивным примером и текущими типами Bridge. По пункту 7 допущений spec.md до завершения планирования необходимы актуальная документация и настоящая проба запуска и переходов. Порядок и свидетельства определены в [разделе 0 quickstart](quickstart.md#0-проверить-интеграцию-vk-до-завершения-планирования). До её выполнения контракт запуска и переходов имеет статус неподтверждённого проектного решения; перенос этой проверки на финальную приёмку не допускается без согласованного изменения спеки. При несовместимости корректируются контракт и будущие тесты, не отключается подпись. Неработающий туннель оставляет этап 0 открытым и блокирует последующую живую приёмку, но не возвращает перенос сервера в границы 004.

Исключений из конституции нет. T034/T040/T041 функции 003 остаются открытыми и независимыми от этого плана.
