# Исследование для плана 004

**Дата оформления:** 2026-11-23. Источники просмотрены при планировании 22–23 ноября. Это исследование исходников и документации; живые запуски VK и туннеля не выполнялись.

**Статус исследования:** обязательная проверка VK до завершения планирования открыта. Порядок минимальной пробы и требования к протоколу приведены в [разделе 0 quickstart](quickstart.md#0-проверить-интеграцию-vk-до-завершения-планирования). Ни одно из описанных ниже проектных решений не заменяет её фактических результатов.

## R1. Повторное использование bot

**Решение:** выделить поиск и общий допуск из транспортного обработчика; Mini App хранит контекст отдельно.

**Основание:** [api.py](../../ecoprofi/bot/api.py) объединяет права, события, поиск, карточки и телеметрию. [access.py](../../ecoprofi/bot/access.py) требует личный peer ID и группу из `test_group`. [events.py](../../ecoprofi/bot/events.py) хранит контекст по `(group_id, peer_id, user_id)`: второй диалог участника совпадёт с первым. Повтор сохраняет эффективный запрос, но поиск выполняется заново; готовый ответ не хранится.

**Альтернативы:** служебный ключ в браузере недопустим; фиктивные peer/group ID обходят контракт. Копия поиска/подписки создаёт две политики. Выбраны один runtime, общий поиск и отдельные транспортные хранилища.

## R2. Подписка и происхождение ответа

**Решение:** существующая [ClubMembers](../../ecoprofi/bot/club.py), TTL по умолчанию 60 секунд, утверждённые исключения и общая причина оповещения `club`. Исключение не считается успешной проверкой доступности VK.

**Основание:** объект уже создаётся в `app.state.club`. `visible_versions` возвращает опубликованные версии разрешённых материалов. [cards.py](../../ecoprofi/bot/cards.py) не включает version ID в публичные карточки. [outcomes.py](../../ecoprofi/bot/outcomes.py) может выдавать названия лекций в `Decision.options`, когда карточки пусты.

**История:** отдельная карта версий для всех источников, включая названия уточнения. Недействительный ответ заменяется целиком. Проверка только карточек недостаточна; новый поиск на каждом GET создавал бы скрытые расходы и менял историю.

## R3. Подпись запуска

**Решение:** исходная query-строка в теле POST; выбрать `vk_*`, сохранить пустые значения, отсортировать имена, URL-кодировать пары, вычислить HMAC-SHA256 с защищённым ключом и Base64url без `=`. Сравнить constant-time. Дубли параметров, неверный app ID, неположительный user ID, неверный timestamp/подпись — отказ.

**Источники:** официальный [Python-пример VKCOM](https://raw.githubusercontent.com/VKCOM/vk-apps-launch-params/master/examples/python3.py), [архивный репозиторий](https://github.com/VKCOM/vk-apps-launch-params). Архивный статус означает необходимость живой проверки. Текущие [типы VK Bridge](https://raw.githubusercontent.com/VKCOM/vk-bridge/master/packages/core/src/types/data.ts) содержат поля запуска и `VKWebAppGetLaunchParams`; клиентский объект Bridge сам по себе полномочий не даёт.

**Политика проекта:** возраст до 300 секунд, опережение часов до 60 секунд, query до 16 KiB. Это не нормативы VK. Возобновление действующей сессии допускает исходный подписанный запуск с совпадающим digest старше пяти минут; новую сессию так получить нельзя.

**Альтернативы:** ID от браузера недостоверен. VK ID Web оператора обслуживает индексатор. Обмен запуска на bearer позволяет не пересылать подписанную query на каждом поиске.

Страницы `dev.vk.com`/`dev.vk.ru` о запуске не удалось прочитать через средство исследования. До завершения планирования сверить актуальную документацию и реальный запуск по этапу 0; архивный пример не объявляется текущей гарантией платформы. Контракт подписи и resume остаётся неподтверждённым проектным решением до этой сверки.

## R4. Frontend и переходы

**Решение:** официальный шаблон `vkui-bridge`, TypeScript, один экран. Версии фиксируются lock-файлом при реализации. В [create-vk-mini-app](https://github.com/VKCOM/create-vk-mini-app) документированы Vite, TypeScript и этот шаблон. Отдельный router и самодельная библиотека компонентов не нужны. Eruda и другие отладочные консоли не включаются в сборку испытаний с реальными параметрами запуска.

Bridge инициализируется через `VKWebAppInit`; при необходимости доступность метода проверяется через `supportsAsync`. Источники: [README Bridge](https://github.com/VKCOM/vk-bridge/blob/master/packages/core/README.md), [интерфейс](https://raw.githubusercontent.com/VKCOM/vk-bridge/master/packages/core/src/types/bridge.ts).

Переходы — стабильные HTTPS-ссылки по нажатию, `noopener noreferrer`. Универсальный `VKWebAppOpenLink` в просмотренных типах отсутствует. Номер страницы и интервал видны независимо от поддержки точного перехода. Открытие проверяется отдельно в мобильном и настольном VK.

## R5. HTTPS текущего стенда

**Факт:** официальный [VK Tunnel](https://github.com/VKCOM/vk-tunnel-client) сообщает о недоступности с 02.10.2025; он исключён из рабочего пути.

**Решение:** Cloudflare Quick Tunnel к локальному шлюзу. По [официальной документации](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/) аккаунт и домен не требуются; адрес временный и меняется при запуске. Нет гарантии доступности, лимит 200 одновременных запросов, SSE не поддерживается. Выбран короткий POST и GET-опрос. При смене адреса обновляются настройки Mini App и `MINIAPP_PUBLIC_ORIGIN`.

**Альтернативы:** сервер противоречит очередности поставки. Отдельный хостинг frontend добавляет второй origin. Другой туннель возможен после пробы и обновления плана, но не считается уже работающим резервом.

Доступность из сетей испытателей не подтверждена. До реальных вопросов проверить открытие на телефоне/ПК и отсутствие сохранения query, Authorization и текстов средствами диагностики. Оператор HTTPS-туннеля участвует в передаче трафика; публикация адреса относится к этапу стенда.

## R6. Сессии и хранение

**Решение:** случайный 256-битный bearer, на сервере только SHA-256 digest. На клиенте токен и ID текущего диалога в sessionStorage; сообщения там не сохраняются. Cookies встроенного браузера не становятся зависимостью входа. Защита от HTML-инъекции обязательна: bearer доступен JavaScript.

Восемь часов от создания, без переноса истории в новую сессию. Перезагрузка возобновляет ту же сессию и подписанный запуск. При смене аккаунта — новая сессия. Недоступность sessionStorage допускает хранение в памяти и новый вход после перезагрузки.

Истёкшие сессии каскадно удаляются с вопросами/ответами/контекстом; очистка при запуске и каждые 15 минут. Доступ закрывается сразу по истечении, независимо от физической очистки.

## R7. Очередь и восстановление

**Решение:** постоянная очередь в той же БД, один worker внутри bot. Разрыв HTTP не теряет вопрос; после падения попытка допускает явный повтор с прежним request ID.

**Основание:** [db.py](../../ecoprofi/db.py) использует `autocommit=False`; транзакции явно завершаются до сети. [ai.py](../../ecoprofi/ai.py) синхронный, поэтому рабочий поток естественнее нового async-стека. Блокировки и fencing — в [модели](data-model.md).

**Альтернативы:** длинный POST зависит от тайм-аутов туннеля. In-memory task теряется при перезапуске. Celery/Redis избыточны для четырёх контрольных диалогов.

## R8. Логи и доказательства

**Решение:** `component=bot`, `channel=miniapp`, operation/request ID, попытка, длительность, outcome и версии. Только allowlist полей; без текстов, launch query, bearer, HTTP headers/body.

**Основание:** [telemetry.py](../../ecoprofi/telemetry.py) маскирует известные ключи, но не любой секрет в произвольной строке. Схема operation_log разрешает `bot/indexer`. Access log и validation errors требуют отдельной обработки: нельзя отражать переданные секреты.

**Вывод:** технические решения описаны, но планирование остаётся открытым до этапа 0: актуальная документация, подпись настоящего запуска, перезагрузка, iframe, сеть и переходы на телефоне/ПК. Свидетельства этой пробы предстоит внести сюда. Плитка и полная цепочка готового приложения проверяются затем при реализации и приёмке; ни один живой результат сейчас не заявлен.

## R11. Повторная сверка документации при implement, 2026-11-23

**Результат:** T001 остаётся открытой; T002–T060 не запускались, код и действующий стенд не изменялись. Это не отказ от реализации, а сохранение обязательного последовательного этапа 0.

Прочитаны актуальные официальные страницы:

- [Параметры запуска](https://dev.vk.ru/ru/mini-apps/development/launch-params): `sign` подписывает параметры запуска, `vk_ts` — целое время формирования подписи; параметры доступны через `window.location` и `VKWebAppGetLaunchParams`. Для авторизации `vk_user_id` нужно предварительно проверить подпись.
- [Начало работы с Bridge](https://dev.vk.ru/ru/bridge/getting-started): `VKWebAppInit` отправляют после загрузки библиотеки, до остальных событий и основных ресурсов, в течение 30 секунд после запуска приложения. Это срок инициализации Bridge, не возраст подписи и не срок сессии.
- [Кэш мини-приложений](https://dev.vk.ru/ru/mini-apps/development/cache): после выхода состояние может храниться 15 минут; возврат по тому же URL может восстановить экран через `VKWebAppChangeFragment` и `VKWebAppViewRestore`, а другой URL запускает приложение заново. Поэтому UI должен учитывать восстановление без нового запуска; это не отменяет проверку подписи при создании сессии.
- [Получение параметров запуска](https://dev.vk.ru/ru/bridge/VKWebAppGetLaunchParams): официальные [типы Bridge](https://raw.githubusercontent.com/VKCOM/vk-bridge/master/packages/core/src/types/data.ts) содержат `VKWebAppInit`, `VKWebAppGetLaunchParams`, `vk_ts`, `sign` и остальные поля запуска. `VKWebAppOpenLink` в этих типах не обнаружен; по-прежнему используется обычная HTTPS-ссылка с `noopener noreferrer`, фактический переход проверяется на устройствах.

**Недоступная часть:** основной текст [Подписи параметров запуска](https://dev.vk.ru/ru/mini-apps/development/launch-params-sign) не получен. WebFetch показывает только навигацию/заголовок; прямой HTTP возвращает каркас SPA; изолированный headless Chrome после ожидания оставляет индикатор загрузки. Публичный `documentation.getPage` через `api.vk.ru` без токена возвращает `Access denied: token required`. Токен пользователя для чтения документации не запрашивался и не использовался. Отключение проверки TLS для обхода доменной ошибки backend портала не выполнялось. Официальный архивный Python-пример по-прежнему подтверждает историческую схему `vk_*` → сортировка → URL-кодирование → HMAC-SHA256 → Base64url без padding, но не закрывает требование актуальной документации.

**Политика проекта:** `now-300 ≤ vk_ts ≤ now+60` — сроки проекта, не заявленные ограничения VK. Восьмичасовая сессия, 15-секундный HTTP timeout, 180-секундный бюджет и интервал опроса 2 секунды также не нормативы VK.

**Нужно для продолжения:** основной текст страницы подписи (без секретов), app ID/ссылка созданного Mini App и ссылка/ID тестового сообщества. Затем подготовить изолированную T002, получить временный HTTPS-адрес и попросить владельца сохранить защищённый ключ только в локальных настройках. Для T003 нужны фактические наблюдения на ПК и телефоне; T004 отмечается только после них.

## R12. T001 и T002: документация получена, проба подготовлена, 2026-11-23

**Входные ресурсы владельца:** Mini App `54916430` (`https://vk.ru/app54916430`), название «Найти лекцию по Экобезу». Тестовое сообщество `https://vk.ru/asukp`, публичные метаданные страницы дали `utils.resolveScreenName`: `object_id=227623179`, `type=group`. Владелец подтвердил привязку приложения и настройку запуска из сообщества. Это тестовое сообщество; источник подписки не меняется. Публичная страница была использована только для определения ID, управление ею не выполнялось.

**T001 завершена.** Владелец предоставил основной текст [официальной страницы подписи](https://dev.vk.ru/ru/mini-apps/development/launch-params-sign), сохранённый в `launch-params-sign.md`. Он подтверждает сортировку всех текущих `vk_*`, `param=value` через `&`, URL-кодирование, HMAC-SHA256 с защищённым ключом и Base64. Список возвращаемых параметров может меняться: allowlist конкретных полей для подписи не используется. Прочие источники R11 учтены. Официальные примеры показывают Base64url без `=`, текст про base64 следует читать вместе с ними. Сроки `300/+60` — политика проекта, не требование VK.

**Различия и несоответствие примеров:** Python/PHP-пример использует `urlencode`/`http_build_query` (пробел `+`), JavaScript — `encodeURIComponent` (`%20`), текст приводит `%20`. Сервер пробы строго проверяет HMAC для этих двух документированных представлений; произвольный sign не принимается. В копии PHP/Python `sign=exTIB...` (44 символа) не воспроизводится из показанных данных, в оригинальном Python-пример VKCOM для тех же данных — `htQF...` (43 символа). Тест отклоняет несовместимый sign и проверяет воспроизводимый официальный алгоритм; старый пример без `vk_ts` не принимается как новый вход. Подробная пометка — конец `launch-params-sign.md`. ## R14. Внешний вход: проксируемая A-запись вместо туннеля, 2026-11-23

**Историческое решение; заменено R15 от 2026-11-24.**

**Уточнение владельца:** у роутера белый IP, и он может пробросить нужные порты до ПК через NAT. Вопрос: нужен ли Cloudflare при таком условии.

**Решение:** публичный вход — `https://miniapp.bot-alimony.ru` через **проксируемую A-запись Cloudflare** на белый IP текущего ПК; TLS заканчивается на шлюзе сертификатом Cloudflare Origin CA (режим Full (strict)); NAT 443 → ПК. Процесс `cloudflared` на ПК не запускается. Именованный туннель (R13) и Quick Tunnel (R5) остаются запасными путями, если провайдер закроет входящий 443 или IP окажется динамическим.

**Почему не прямое подключение без прокси:** белый IP сам по себе не даёт двух обязательных вещей — домена и доверенного сертификата (Let's Encrypt не выдаёт сертификаты на IP). Прямая A-запись технически возможна, но публикует домашний IP всем участникам, лишает защиты от перебора и требует автоматизации продления сертификата. Прокси Cloudflare при том же белом IP скрывает origin, даёт WAF и Origin CA со сроком 15 лет без продления.

**Следствия в конфигурации:** шлюз публикует `443:443`; TLS-серверный блок вынесен в `deploy/miniapp-tls.conf` и подключается из `conf.d/tls/*.conf`, поэтому образ без сертификатов поднимается только на `127.0.0.1:8080` (этим пользуется T027). Добавлены `deploy/miniapp-realip.inc` (диапазоны CF от 2026-11-23, `real_ip_header CF-Connecting-IP`) и `deploy/miniapp-server.inc` (общие локации для обоих server-блоков). Без восстановления реального адреса лимит 10 r/s считался бы на edge-узел Cloudflare, а не на участника.

**Не проверено:** фактическая достижимость входящего 443 снаружи, статичность IP, выдача Origin CA сертификата, режим Full (strict) и `nginx -t` на собранном образе. До этих наблюдений T028/T058/T059 остаются открытыми; вариант с туннелем не объявляется неработающим. Доверие `CF-Connecting-IP` допустимо только при входящем 443, ограниченном диапазонами Cloudflare.

**Архитектура:** канал, подпись, origin интерфейса и API, общий bot/каталог не изменились; меняется только способ доставки HTTPS. Правка `Архитектура_бота_Экопрофи.docx` не требуется.
