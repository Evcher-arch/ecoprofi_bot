# План реализации поиска по слайдам и письмам

**Функция** 002-slides-letters-schedule · [Спецификация](spec.md) · 2026-11-22

## Результат и границы

Стенд 001 на ПК разработчика получает расписание как источник состава корпуса. Индексатор читает расписание, связывает строки с публикациями, обрабатывает презентации и письма 5–10 выбранных лекций и публикует их рядом с записями 001. Участник в том же тестовом диалоге получает страницу презентации, письмо с реквизитами или эпизод записи с указанием лекции. Приёмка охватывает VK-01, DOC-01 и часть NET-01, относящуюся к документам; итог измеряется на 20 вопросах редактора.

Вне плана: мини-приложение, сервер клуба и автономный доступ оператора (OPS-01), распознавание речи, обход документов всего расписания, интерфейс редактора.

## Технический контекст

| Параметр | Значение |
| --- | --- |
| Язык и среда | Python 3.12 в контейнере (проект требует 3.11+), Docker Compose на Windows |
| Основа из 001 | FastAPI, psycopg 3, pgvector, httpx; PostgreSQL 16 с pgvector; Yandex AI Studio для эмбеддингов (256) и пояснений |
| Новые зависимости индексатора | pypdfium2 (текст и растеризация страниц), Tesseract с русской моделью и pytesseract, Pillow, striprtf |
| Хранилище | Тот же том PostgreSQL; миграция `002_documents.sql` без потери данных 001 |
| Тесты | pytest; интеграционные — на отдельной БД в памяти; VK, AI Studio и сеть заменены фикстурами; распознавание в тестах настоящее, на маленькой странице-скане |
| Вид проекта | Сервисы bot, indexer, vk-adapter и одноразовые команды оператора |
| Объём | 5–10 лекций; порядка сотен страниц и десятков писем; расписание — около 280 ссылок |
| Производительность | Порогов нет: длительность распознавания страницы, обновления лекции и ответа измеряется на пилоте (конституция, «Каналы и эксплуатация») |
| Ограничения | Оригиналы не хранятся; подписанные адреса файлов и токены не пишутся в БД и журналы; распознавание только локальное; токен оператора вводится вручную |

Неизвестные, от которых зависит реализация, вынесены в пробы R1, R4, R5, R7, R9 в [основаниях решений](research.md). Нерешённых вопросов, блокирующих проектирование, нет.

## Границы компонентов

| Компонент | Что меняется | Доступ |
| --- | --- | --- |
| db | Лекции с датой и состоянием, связи материалов с публикациями, фрагменты трёх видов, решения редактора | Без изменений: отдельные роли bot и indexer |
| indexer | Разбор расписания; обнаружение документов в публикациях; извлечение текста страниц и писем; распознавание; отчёт редактору | Токен оператора VK, эмбеддинги документов, запись в каталог. Образ с Tesseract |
| bot | Поиск по фрагментам всех видов; подтверждение по названию и реквизитам; группировка по лекциям; карточки `page`, `letter`, `material`; импорт политики версии 2; команда оценки | Чтение каталога и прав. Образ без Tesseract |
| vk-adapter | Не меняется: отправляет `text` ответа | Ключ сообщений и служебный ключ |

## Порядок реализации

1. **Пробы.** Выполнить R1 (расписание без входа), R4 (распознавание страницы 2 контрольной презентации), R5 (реквизиты контрольного письма), R7 (прямая ссылка на документ), R9 (предел входа эмбеддингов). Записать наблюдения в протокол. Сохранить обезличенные фрагменты расписания, страницу-скан и письмо как фикстуры. Провал R4 возвращает решение владельцу.
2. **Схема и перенос.** Миграция 002: лекция с датой и состоянием, `material_link`, вид и тип объекта у материала, реквизиты, `fragment` вместо `episode`, расширение `material_policy` и `index_job`, выборка пилота. Проверить на копии данных 001: контрольный вопрос даёт тот же эпизод. Разделить образ на общую цель и цель индексатора.
3. **Расписание.** Разбор строк: дата, раздел, название, ссылки на публикации, пометка «Клуб» у конкретного материала, «в разработке». Ключ строки по R2. Повторный разбор без дублей; осиротевшие строки. Перепривязка материалов 001 от условной строки к настоящей. Отчёт редактору.
4. **Аудитория.** Действующая аудитория по правилам [модели данных](data-model.md): сигнал расписания и платной ленты, решение редактора с «увиденным сигналом», строгое правило при расхождении. Импорт политики версии 2 с приёмом версии 1.
5. **Документы.** Обнаружение вложений и упоминаний в публикациях за один проход по ленте; чтение файла в память с проверкой сигнатуры и предела размера; страницы PDF с текстовым слоем и распознаванием; порог читаемости R10; письма RTF с реквизитами по R5 и R6; деление на фрагменты по R9. Публикация версии через существующий механизм `publish.py`: один сбойный материал не задерживает остальные, повторяется только он.
6. **Поиск и карточки.** Запрос по `fragment` с фильтром действующей аудитории в обоих каналах; подтверждение с учётом поисковой подписи материала (R11); группировка по лекциям и предел двух карточек на лекцию (R12); карточки и текст сообщения по [контракту](contracts/search-cards.md). Модель по-прежнему получает только разрешённые выдержки и идентификаторы кандидатов.
7. **Оценка и приёмка.** Команда оценки по файлу вопросов; калибровка порогов слабого совпадения и близости лекций на 20 вопросах; живой прогон по [руководству](quickstart.md) с протоколом.

Шаги 3–4 и шаг 5 независимы после шага 2 и могут идти параллельно; шаг 6 зависит от обоих.

## Проверка конституции

| Принцип | Решение и приёмка | Итог |
| --- | --- | --- |
| I. Состав корпуса определяется расписанием | Корпус строится от строк расписания; строка «в разработке» хранится; сохраняются идентификаторы VK, стабильная ссылка, версия и вид связи; пометка «Клуб» действует на материал; неясную аудиторию решает редактор. FR-01–FR-03, SC-01. | Соблюдён. Выборка 5–10 лекций — граница релиза, подтверждает владелец |
| II. Права проверяются до поиска | Действующая аудитория вычисляется при каждом поиске; фрагменты всех видов наследуют её; фильтр — до обоих каналов поиска и до передачи модели; перепроверка перед возвратом и повторной доставкой. Проверка параметров запуска Mini App к этой функции не относится. FR-09, SC-04. | Соблюдён |
| III. Рекомендация подтверждается источником | Страница — текстом этой страницы; реквизиты — текстовым слоем оригинала; интервал — дорожкой. Без подтверждения — карточка материала целиком или отказ. Ссылки и координаты берёт сервер из каталога. FR-04–FR-08, FR-10, SC-02, SC-03. | Соблюдён |
| IV. Целостность опубликованного индекса | Файл обрабатывается в памяти и не сохраняется; фрагмент связан с версией, аудиторией и местом в источнике; модель эмбеддинга фиксируется; повтор не создаёт дублей; версия переключается атомарно; раздельные статусы сбоев; повтор только затронутого материала. FR-11–FR-13, SC-07. | Соблюдён |
| V. Воспроизводимая приёмка | Пробы и живой прогон записываются с датой, средой, ролью и наблюдением; протокол разделяет автоматическую проверку, ответ и наблюдение в документе; оценка на 20 вопросах повторяется командой. SC-05, SC-06. | Соблюдён |
| Внешняя обработка | Распознавание локальное. Во внешний сервис уходят только тексты для векторизации и выдержки для пояснения — как разрешено принципом II. | Поправка к конституции не требуется |

Повторная проверка после проектирования: нарушений нет. Два места, где план опирается на решение владельца (принцип I и «Порядок изменений»): правило «более строгая аудитория» для материалов 001 и перечень лекций выборки.

## Структура реализации

```text
ecoprofi/
├── indexer/
│   ├── schedule.py      # разбор расписания, ключи строк, связи      (новый)
│   ├── documents.py     # чтение файла, сигнатура, страницы, письма   (новый)
│   ├── ocr.py           # распознавание и порог читаемости            (новый)
│   ├── report.py        # отчёт редактору                             (новый)
│   ├── vk_sources.py    # + вложения-документы, проход по ленте
│   ├── publish.py       # + фрагменты страниц и писем
│   └── __main__.py      # + --schedule-file/--schedule-url, --materials, --report
├── bot/
│   ├── access.py        # + действующая аудитория материала
│   ├── search.py        # fragment, подпись материала, группировка по лекциям
│   ├── outcomes.py      # + близость лекций
│   ├── cards.py         # + page, letter, material; текст сообщения
│   ├── import_policy.py # + версия 2
│   └── evaluate.py      # оценка по файлу вопросов                    (новый)
migrations/002_documents.sql
tests/
├── fixtures/            # + расписание, PDF с текстом, PDF-скан, RTF
├── test_schedule.py, test_documents.py, test_ocr.py
└── integration/         # + test_migration_002.py, test_audience.py,
                         #   test_document_search.py, test_evaluate.py
Dockerfile               # цели сборки app и indexer
compose.yaml             # indexer и tests — на образе indexer
```

Проверки 001 сохраняются и должны проходить без правок ожиданий, кроме переименования `episode` → `fragment` в запросах тестов.
