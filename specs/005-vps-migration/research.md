# Исследование 005: перенос стенда на VPS

**Дата:** 2026-11-24. **Основание:** [spec.md](spec.md), [R16 research 004](../004-vk-mini-app/research.md#r16-закрытие-004-и-перенос-на-vps-2026-11-24), [next-stages §3](../004-vk-mini-app/next-stages.md).

В спецификации нет пунктов `NEEDS CLARIFICATION`. Выбор провайдера оставлен владельцу (допущение 2). Ниже закреплены критерии выбора и решения, которые уже приняты в файлах развёртывания (T001–T004), а также пробелы, найденные при сверке спеки, кода и tasks.md. Живые пробы на VPS при планировании не выполнялись: сервер ещё не заказан.

## R1. Провайдер и тариф

- **Решение:** провайдера выбирает владелец по критериям FR-01 и допущения 2: российский ЦОД (Москва/СПб), KVM, NVMe, статический IPv4, S3-совместимое хранилище в том же аккаунте, по возможности зеркало Docker Hub. Рекомендуемый тариф — 4 vCPU / 8 ГБ / 80 ГБ. Перед заказом цифры сверяются с T006.
- **Обоснование:** нагрузку создают PostgreSQL с pgvector, Tesseract в индексаторе и сборка образов на сервере (пик около 2 ГБ). Модели работают в Yandex AI Studio, а ASR вынесен на ПК владельца (spec, «Решение о транскрибации»). Поэтому GPU и запас под Whisper не нужны.
- **Отклонено:** зарубежный VPS (та же проблема региональной доступности, что у Cloudflare, и вопросы локализации данных участников); OpenVZ/LXC (Docker внутри контейнерной виртуализации работает ненадёжно); сборка образов на ПК с переносом через `docker save` (нарушает граничный случай «сборка не в обход»).

## R2. Публичный вход без Cloudflare

- **Решение:** A-запись `miniapp` в зоне REG.RU указывает на IPv4 VPS. TLS заканчивается на nginx шлюза (`deploy/vps/miniapp-nginx.conf`). Порт 80 отдаёт только ACME и делает 301 на https, порт 443 отдаёт `miniapp-server.inc`. Для чужих имён и обращений по IP действует `ssl_reject_handshake on`. Порт 8080 открыт только на `127.0.0.1` для диагностики.
- **Обоснование:** R16 фиксирует, что Cloudflare в регионе нестабилен. Прямой вход убирает промежуточного посредника, а origin `https://miniapp.bot-alimony.ru` и настройки приложения 54916430 остаются прежними (FR-04). Образ шлюза не меняется: конфиг для VPS монтируется поверх `default.conf`, общие `*.inc` берутся из образа.
- **Отклонено:** другой CDN или обратный прокси (снова посредник с той же неопределённостью доступности); отдельный хостовой nginx или Caddy (второй экземпляр allowlist, расхождение с образом 004).

## R3. Адрес участника и `limit_req`

- **Решение:** `miniapp-realip.inc` не подключается. `$binary_remote_addr` берётся из TCP-соединения. При публикации порта Docker через iptables DNAT исходный адрес клиента сохраняется (userland-proxy работает только для loopback и hairpin-соединений).
- **Обоснование:** без Cloudflare заголовок `CF-Connecting-IP` подделывается клиентом. Доверять ему нельзя (FR-04).
- **Проверка:** в T037 убедиться, что лимит 429 срабатывает для одного клиента и не мешает другому. Отдельный тест в репозитории не нужен.

## R4. Сертификат Let's Encrypt и продление

- **Решение:** первичный выпуск выполняется командой `certbot --standalone` при свободном порту 80 (T018). После запуска шлюза продление переключается на webroot `/var/www/certbot` командой `certbot reconfigure` (T024). Deploy-хук выполняет `nginx -s reload` в контейнере шлюза. Продлевает `certbot.timer` из пакета Ubuntu.
- **Обоснование:** standalone-продление при занятом порту 80 сорвётся. Webroot смонтирован в шлюз только для чтения, а certbot пишет туда с хоста.
- **Пробел:** граничный случай спеки требует оповещения за 14 дней до истечения. Let's Encrypt прекратил рассылку писем об истечении в 2025 году, а в tasks.md такой задачи нет. Решение — R10.

## R5. DNS: возврат зоны на REG.RU

- **Решение:** по допущению 1 зона возвращается на NS REG.RU, сайт и туннель в Cloudflare удаляются (T009).
- **Риски (учтены в T008):**
  1. **DNSSEC.** Если для домена в REG.RU записан DS от Cloudflare, после смены NS валидирующие резолверы (8.8.8.8, 77.88.8.8, сети операторов) вернут SERVFAIL. До смены NS нужно отключить DNSSEC в Cloudflare и удалить DS у регистратора, затем дождаться TTL DS. Проверка: `Resolve-DnsName bot-alimony.ru -Type DS -Server 8.8.8.8` возвращает пустой ответ.
  2. **CAA.** Если в зоне есть CAA, при переносе нужно оставить `letsencrypt.org`, иначе T018 получит отказ.
  3. **TTL.** На время переноса A-запись создаётся с TTL 300, после приёмки TTL можно поднять.
- **Отклонено:** оставить зону в Cloudflare в режиме только DNS. Это не противоречит прямому входу, но владелец решил уйти из Cloudflare полностью.

## R6. Docker и ufw на Ubuntu 24.04

- **Решение:** Docker ставится из официального репозитория (FR-02). Наружу публикуются только `80:80` и `443:443` шлюза (`compose.vps.yaml`), остальные сервисы работают в сети `internal`, у шлюза есть `127.0.0.1:8080`. ufw закрывает хостовые порты, внешнее сканирование в T025 подтверждает итог.
- **Обоснование:** правила Docker в цепочке `DOCKER` применяются раньше ufw. Поэтому закрытость обеспечивает отсутствие `ports`, а не ufw.
- **Дополнение — журналы контейнеров:** драйвер `json-file` по умолчанию не ротирует журналы. За семь суток наблюдения и после них журналы растут без ограничения. В `/etc/docker/daemon.json` (тот же файл, что в T015) задаётся `"log-driver": "json-file", "log-opts": {"max-size": "10m", "max-file": "5"}`. Настройка применяется к контейнерам, созданным после перезапуска Docker, поэтому выполняется до T022.

## R7. Перенос данных

- **Решение:** `pg_dump -Fc` при остановленных писателях → SHA256 → scp → `pg_restore --exit-on-error` в БД, созданную init-скриптом → `migrate` (новых миграций нет) → сверка `deploy/table-counts.sql` (T026–T030).
- **Проверено по коду:**
  - `db/init/01_roles.sh` создаёт роли `ecoprofi_bot` и `ecoprofi_indexer` и `CREATE EXTENSION IF NOT EXISTS vector`. pg_dump записывает расширение как `CREATE EXTENSION IF NOT EXISTS`, поэтому `--exit-on-error` на нём не падает. Другие объекты в `public` init-скрипт не создаёт.
  - Владельцем объектов в обеих БД является `ecoprofi_owner`, права выдаются ролям с одинаковыми именами.
  - Таблица учёта миграций — `schema_migrations(name)`, её проверяет `table-counts.sql`.
- **Дополнение — статистика планировщика:** pg_restore в PostgreSQL 16 не переносит статистику. После T029 и перед T031 нужно выполнить `vacuumdb -U ecoprofi_owner -d ecoprofi --analyze-only`, иначе первые поиски могут пойти мимо индексов. Время поиска (SC-01, p95) иначе будет измерено на неподготовленной БД.
- **Дополнение — версии:** на обеих площадках записать `SELECT version()` и `SELECT extversion FROM pg_extension WHERE extname='vector'`. Тег `pgvector/pgvector:pg16` плавающий, и минорная версия на VPS может быть новее. Чтение более старого дампа поддерживается, обратный перенос (T050) требует, чтобы на ПК версия была не ниже. При возврате на ПК образ там нужно обновить.
- **Отклонено:** логическая репликация (избыточна для объёма в единицы ГБ и часового окна); перенос тома Docker как файлов (зависит от совпадения версий и не даёт контрольной сверки).

## R8. Один рабочий контур и доступ оператора

- **Решение:** порядок «стоп писателей ПК → снимок → восстановление и сверка → запуск VPS → стоп `db` ПК и снятие автозапуска» (T026–T032). Доступ оператора на VPS получается новым входом `access login` (T033). Том `indexer-secrets` не копируется.
- **Проверено по коду:** вход работает на сервере без браузера. Команда печатает адрес VK ID, оператор открывает его у себя, а адрес `https://localhost/callback?...` вставляет обратно в CLI (`ecoprofi/indexer/access.py`, `REDIRECT`). Проброс портов не нужен.
- **Следствия:**
  - На томе ПК остаётся прежняя пара доступа. Любой запуск индексатора на ПК, включая разовые команды, продлит её на второй площадке. Это противоречит next-stages §3 п. 5, поэтому после T032 команды индексатора на ПК не выполняются. При возврате (T050) на ПК нужен новый вход, пару с VPS тоже не копируют.
  - next-stages §3 п. 2 требует наблюдать продление рабочего доступа, отзыв и повторный вход на сервере. T033–T034 покрывают только вход и чтение. Продление наблюдается по `indexer status` за семь суток (T051). Отзыв с повторным входом репетируется отдельно, по решению владельца о моменте.
- **Long Poll:** при запуске на VPS `vk-adapter` получает новый сервер и `ts`. Сообщения тестового канала за время окна могут не обработаться. Mini App от этого не зависит. Это допустимо, участников предупреждают об окне.

## R9. Резервная копия

- **Решение:** `deploy/backup.sh` запускается из `ecoprofi-backup.timer` в 03:30 МСК от пользователя `deploy`. Порядок: дамп → проверка `pg_restore --list` → sha256 → rclone в `daily/`, по воскресеньям ещё в `weekly/` → ротация 8 и 29 дней → локально 3 копии. Пробное восстановление выполняется в изолированном контейнере без сети `internal` (T048).
- **Обоснование:** копия хранится вне VPS (FR-09), ключ S3 лежит только в конфиге rclone с правами 600. systemd задаёт `HOME` для `User=`, поэтому rclone находит `~deploy/.config/rclone/rclone.conf`. Восстановленная копия не запускает bot и индексатор и сама не опрашивает VK.
- **Пробел:** при сбое юнита ночная копия молча не создаётся. В спеке «нет свежей копии» есть только в диагностике quickstart, оповещения нет. Решение — R10.

## R10. Оповещения хоста: сертификат и копия

- **Решение:** использовать существующую очередь `alert` (миграция 003) без изменения кода приложения. Хостовой скрипт `deploy/host-alert.sh open|close <причина> [текст]` пишет в таблицу через `docker compose exec -T db psql` от роли владельца. Правила 003 сохраняются: одна открытая запись на причину, напоминание раз в сутки, одно сообщение о восстановлении. Доставляет их `vk-adapter`, как и прочие оповещения. Новые причины — `tls` и `backup` ([contracts/host-alerts.md](contracts/host-alerts.md)).
  - `tls`: таймер `ecoprofi-cert-check.timer` раз в сутки проверяет срок сертификата через `openssl x509 -checkend`. Если осталось меньше 14 дней, причина открывается, иначе закрывается.
  - `backup`: `OnFailure=` у `ecoprofi-backup.service` открывает причину. Успешный запуск `backup.sh` закрывает её последним шагом.
- **Обоснование:** `alert.cause_key` — свободный текст, а `bot.alerts.pending()` выдаёт любые открытые записи. Поэтому новые причины не требуют миграции и не меняют код (допущение 4 спеки). Получатель тот же — `ALERT_VK_USER_ID`.
- **Отклонено:** письма Let's Encrypt (прекращены); внешний мониторинг (новый сервис и учётная запись, решение владельца, см. R11); отдельный бот или почта на VPS (ещё один секрет и канал).
- **Ограничение:** если остановлен весь VPS или `vk-adapter`, хостовое оповещение тоже не уйдёт. Это закрывает R11.

## R11. Недоступность всего сервера

- **Решение для 005:** причина `stale` (bot) срабатывает, только когда работает bot. При полной недоступности VPS сообщить некому. Это фиксируется как известное ограничение. Внешнюю проверку доступности (любой сервис мониторинга HTTPS из РФ с уведомлением владельцу) владелец может подключить по желанию. Секреты и код для неё не нужны. Выполнение SC-06 оценивается по журналу проходов, а не по отсутствию оповещений.
- **Обоснование:** внешний сервис означает новую учётную запись и передачу адреса третьей стороне, а это решение владельца. Для приёмки он не обязателен.

## R12. Проверка оверлея без Docker на ПК

- **Решение:** `nginx -t` и `docker compose ... config -q` выполняются на VPS в T020, потому что на ПК разработки Docker не установлен (tasks.md, статус).
- **Риск, который нужно проверить в T020:** в `compose.yaml` на верхнем уровне объявлен секрет `miniapp_tunnel_token` с файлом `./deploy/secrets/cloudflared-token.txt`, а на VPS этот файл не переносится (T019). Если Compose откажется загружать проект без файла даже при неактивном профиле `tunnel`, нужно создать пустой файл-заглушку с правами 600 (`install -m 600 /dev/null deploy/secrets/cloudflared-token.txt`). Каталог исключён из Git (`.gitignore: deploy/secrets/`), а туннель на VPS не запускается. Выбранный путь записывается в acceptance.md.

## R13. Согласование с архитектурой
