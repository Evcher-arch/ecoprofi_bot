# Запуск и приёмка автономного индексатора

Целевой порядок проверки **после реализации**. Рабочая папка — корень проекта на Windows с Docker Compose; стенд 002 работает. Команды — в [контракте оператора](contracts/operator-commands.md), оповещения — в [контракте оповещений](contracts/alerts.md), состояния — в [модели данных](data-model.md).

Нужны: номер приложения VK ID (`VK_ID_APP` в `.env`), учётная запись оператора с доступом к платной ленте, идентификатор оператора для оповещений (`ALERT_VK_USER_ID`); оператор заранее пишет любое сообщение тестовому сообществу. Docker Desktop настроен на запуск при входе в Windows.

Ниже `ix` означает `docker compose run --rm indexer python -m ecoprofi.indexer`.

## 0. Автоматические проверки

```powershell
docker compose build
docker compose --profile test run --rm tests
```

Ожидается: проверки 001 и 002 проходят без правок ожиданий; новые покрывают продление с заменой токена, аварийную остановку между ответом и записью, отказ авторизации посреди прохода, продолжение прохода с незавершённой порции, плановый запуск и пропущенные сроки, запрет параллельного прохода, постоянный сбой, ограничение частоты, открытие, напоминание и закрытие оповещений. VK, VK ID и AI Studio заменены подменами; время подставляется.

## 1. Обновить схему и снять копию

```powershell
docker compose exec db pg_dump -U ecoprofi_owner ecoprofi > out/backup-before-003.sql
docker compose run --rm bot python -m ecoprofi.bot.migrate
docker compose up -d bot vk-adapter
```

Ожидается: миграция 003 применена, повторный запуск сообщает об отсутствии изменений; счётчики каталога прежние (140 лекций, 15 материалов, 572 фрагмента); «ВЧ-09-03-34/3616» возвращает письмо.

## 2. Войти один раз (история 2)

```powershell
ix access login
ix access check
ix status
```

Ожидается: после входа — «доступ сохранён, платная лента читается» с числом постов (ориентир пробы — 1039; это число — точка отсчёта для проверки платной ленты); `status` показывает состояние `active` и срок рабочего токена. В выводе команд нет значений доступа. В протокол записывается состав ответа VK ID без значений, включая срок токена обновления, если он указан (R6), и результат пробы `wall.getById` (R10).

## 3. Полный проход с остановками (SC-01, SC-02, SC-07)

```powershell
ix run full
```

1. Во время второй порции задать боту «ВЧ-09-03-34/3616» из учётной записи подписчика клуба — ответ прежний. Из учётной записи без подписки — отказ с текстом про клуб, без карточек.
2. Остановить стенд посреди порции (`docker compose down`), включить, повторить `ix run full`: проход продолжается с незавершённой порции. Повторить остановку ещё раз в другом месте.
3. Проход длится дольше часа: в `status` время последнего продления меняется без входа оператора (SC-03, часть).
4. По окончании — сводка по итоговым состояниям; оператор получает сообщение с итогом. Материалов без состояния — ноль.
5. Повторить `ix run full`: ноль новых версий, материалов и связей.

В протокол: длительность, число порций, итог по состояниям, число обращений к внешней обработке, места двух остановок, счётчики до и после повторного прохода.

## 4. Проверить повторный вход (SC-06, FR-14)

1. Отозвать доступ приложения в кабинете VK ID. Выполнить `ix access check` (при необходимости — после истечения рабочего токена): состояние `login_required`, код выхода 3.
2. Оператор получает одно сообщение «нужен вход»; повторный `ix access check` второго сообщения не даёт.
3. `ix access login` — приходит сообщение о восстановлении; `ix run update` выполняется.
4. `ix access forget`, затем `ix run update`: код 3, источники не читаются. Снова `ix access login`.

В протокол: время от отзыва до отказа, время от отказа до сообщения, тексты сообщений.

## 5. Включить расписание (SC-05)

```powershell
ix schedule set 07:00 19:00
ix schedule on
docker compose up -d indexer-daemon
```

Ожидается: `schedule on` проходит только после шагов 2 и 4. `status` показывает плановые проходы, начавшиеся не позже 07:15 и 19:15, и ноль переобработанных материалов. Команда `ix schedule set 07:00 12:00 19:00` получает отказ.

Отдельные наблюдения:

- назначить срок на ближайшие минуты и запустить в это время `ix run update`: плановый запуск записан как пропущенный, параллельного прохода нет;
- остановить стенд до срока и включить после: выполняется одно обновление, автоматических обновлений за сутки не больше двух;
- `ix schedule off`: в срок обновление не начинается;
- остановить только `indexer-daemon` при включённом расписании: в течение 15 минут после срока приходит оповещение `stale`.

## 6. Неделя автономной работы (SC-03, SC-04, SC-05, SC-09)

Семь суток стенд работает без команд оператора, кроме вызванных оповещением. Ежедневно в протокол: время начала планового прохода, исход, время последнего продления. По окончании:

```powershell
ix status
docker compose logs --no-color > out/logs-week.txt
```

Проверяющий ищет известные фрагменты значений доступа в `out/logs-week.txt`, отчёте редактора, таблице оповещений и репозитории — ожидается ноль совпадений (значения берутся из файла хранилища на время проверки и в протокол не вносятся). В протокол записывается фактический срок работы без входа; при входе оператора на другом устройстве — пережил ли его доступ индексатора (R6).

## 7. Постоянный сбой и новый материал

- После трёх проходов документы `doc177068782_672441135` и `doc177068782_672441136`, если по-прежнему дают HTTP 504, переходят в постоянный сбой: по одному сообщению на материал, в следующих проходах они не читаются. `ix requeue <ключ>` возвращает материал в очередь.
- Когда в расписании лекций появляется новая ссылка, после ближайшего планового прохода материал находится в поиске либо числится в «ждёт решения редактора».

Протокол приёмки ведётся в `specs/003-autonomous-indexer/acceptance.md` и разделяет автоматическую проверку, наблюдение на стенде и наблюдение оператора в VK (принцип V). Значения доступа, коды и адреса файлов в протокол не вносятся.
